# گزارش کیفیت داده — بک‌فیل MT5 (SPEC.md ۴.۱)

اجرا شده در ۲۰۲۶-۰۹-۱۵ روی جدول `candles` واقعی (نماد `XAUUSD@`، بازه ۲۰۲۳-۰۹-۱۵ تا ۲۰۲۶-۰۹-۱۵، هر ۴ تایم‌فریم).

## ۱. یکپارچگی OHLC — کوئری واقعی روی جدول

```sql
SELECT tf,
  count(*) FILTER (WHERE high < low)                                   AS high_lt_low,
  count(*) FILTER (WHERE high < open)                                  AS high_lt_open,
  count(*) FILTER (WHERE high < close)                                 AS high_lt_close,
  count(*) FILTER (WHERE low > open)                                   AS low_gt_open,
  count(*) FILTER (WHERE low > close)                                  AS low_gt_close,
  count(*) FILTER (WHERE open<=0 OR high<=0 OR low<=0 OR close<=0)     AS non_positive_price,
  count(*) FILTER (WHERE ts_utc > now())                               AS future_ts
FROM candles WHERE symbol = 'XAUUSD@' GROUP BY tf ORDER BY tf;
```

| tf  | high<low | high<open | high<close | low>open | low>close | قیمت≤۰ | ts_utc در آینده |
|---|---|---|---|---|---|---|---|
| H1  | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| M1  | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| M15 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| M5  | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

**نتیجه: صفر مطلق در همه‌ی موارد، همه‌ی تایم‌فریم‌ها.** تصحیح نسبت به گزارش قبلی: ادعای «نوع `numeric` این را تضمین می‌کند» غلط بود — `numeric` فقط عددی‌بودن را تضمین می‌کند، نه رابطه بین ستون‌ها. این بار واقعاً کوئری خورد، نه فرض.

## ۲. آفست زمانی بروکر — عدد و روش

**آفست اندازه‌گیری‌شده:**
- تابستان (DST فعال): **UTC+3**
- زمستان (DST غیرفعال): **UTC+2**

**چطور قطعی شد (نه حدس):**
۱. **آفست لحظه‌ای:** یک تیک زنده‌ی MT5 (`symbol_info_tick`) در لحظه‌ی `2026-09-15 13:29:37` (به‌وقت سرور بروکر) با ساعت سیستم لینوکس اوبونتو که NTP-sync است (`2026-09-15 10:29:37 UTC`) مقایسه شد → اختلاف دقیقاً ۳ ساعت.
۲. **قانون DST:** چون این تاریخ داخل بازه‌ی DST هر دو تقویم آمریکا و اروپا بود، به‌تنهایی کافی نبود که مشخص کند بروکر کدام تقویم را دنبال می‌کند یا اصلاً DST دارد یا نه. برای این، **کل تاریخچه‌ی H1 از ۲۰۱۹ تا ۲۰۲۶ (۴۴۷۰۳ کندل)** اسکن شد و هر شکاف آخرهفته‌ای (>۲۰ ساعت) استخراج شد. الگوی بسته‌شدن جمعه‌ها ثابت ماند (۲۳:۰۰ به‌وقت بروکر تقریباً همیشه)، ولی زمان بازگشایی یکشنبه دقیقاً یک ساعت زودتر می‌افتاد در یک هفته‌ی خاص هر سال — این هفته‌ها با تقویم‌های شناخته‌شده تطبیق داده شدند:
   - شروع تغییر (بهار): **دقیقاً جمعه‌ی قبل از دومین یکشنبه‌ی مارس** (قاعده‌ی آمریکا) — تطبیق کامل، صفر استثنا، برای هر ۷ سال (۲۰۲۰ تا ۲۰۲۶).
   - پایان تغییر (پاییز): **دقیقاً جمعه‌ی قبل از آخرین یکشنبه‌ی اکتبر** (قاعده‌ی اروپا) — تطبیق کامل، صفر استثنا، برای هر ۶ سال (۲۰۲۰ تا ۲۰۲۵).

**نتیجه‌ی صادقانه:** این یک قاعده‌ی **ترکیبی و غیرمعمول** است — نه EET خالص (که هر دو تاریخش اروپایی است)، نه قاعده‌ی معمول «سرور = نیویورک+آفست ثابت» (که هر دو تاریخش آمریکایی است). هیچ منبع مستند رسمی از WM Markets پیدا نشد که این را تایید کند (جست‌وجو شد، چیزی نبود). **این قاعده حدس یا پیش‌فرض نیست** — از داده‌ی واقعی خودِ این بروکر، با صفر استثنا در ۷ سال، استخراج شده. ولی *چرا* بروکر دقیقاً همین ترکیب را انتخاب کرده، مشخص نیست و اهمیتی هم ندارد — چیزی که مهم است این‌ است که این الگو تکرارشونده و قابل اعتماد است، نه اینکه دلیلش را بفهمیم.

**ریسک باقی‌مانده:** این قاعده بر پایه‌ی ۷ سال داده‌ی گذشته است. اگر بروکر *در آینده* سیاست DST‌اش را عوض کند (نادر ولی ممکن)، این کد بدون خبردادن اشتباه می‌کند. پیشنهاد: یک چک دوره‌ای (مثلاً سالانه، نزدیک هر دو تاریخ گذار) که آفست زنده را با آنچه کد پیش‌بینی می‌کند مقایسه کند — این را الان نساختم چون خارج از scope این پرامپت است، ولی باید جایی ثبت بماند.

پیاده‌سازی: `src/ingest/timezones.py`. تست: `tests/ingest/test_timezones.py` (۱۱ تست، شامل تطبیق دقیق با هر ۷ تاریخ گذار واقعی بالا).
